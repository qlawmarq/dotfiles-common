# memory-consolidate

auto-memory は事象ごとに 1 件ずつ足されていくので、同じ原則が複数のファイルに分かれ、プロジェクト資料に取り込まれた内容を要約して持ち続け、存在しないファイルへのリンクや終わった作業の経緯を抱えたままになる。
Claude Code は `MEMORY.md` が読み込み上限（先頭 200 行か 25KB の小さい方）に近づくまで何も言わない。
このスキルは、変更前に棚卸しを報告し、了承を得てから統合・委譲・削除を行う。

扱うのは重複・委譲・古さだけで、メモリの原則そのものの是非は裁かない。原則を変えたい話が出たら、ユーザーとの対話に移る。

## 進め方の要点

- 了承の前には何も変更しない。了承後もバックアップを取るまでは書き込まない。
- 削除すべきか迷うものは、まとめて決めずに 1 件ずつ相談する。
- リンクは、リンク先の実在を確かめてから書く。
- 古い情報は痕跡を残さず消す。「旧〜」「〜へ移設済み」「〜は廃止」と書き残さない。履歴は git と会話記録が持つ。

## 1. 対象を決める

1. メモリディレクトリを決める。システムプロンプトの auto-memory の節にパスが書かれていれば、それを使う。ユーザーがパスを渡した場合はそれを使う。どちらもなければ `scripts/inventory.py` の解決に任せる（`autoMemoryDirectory` 設定 → git の主 worktree のルートから導いたパス）。worktree 間で同じディレクトリを共有するので、どの worktree から実行しても対象は同じになる。
2. プロジェクトのルートを決める。通常は git のルート。メモリがリポジトリ外（サブディレクトリ単位など）を指していれば、それに合わせて `--project-root` を渡す。
3. メモリディレクトリに `.consolidate-lock` があれば、組み込みのバックグラウンド統合（auto-dream）が動いている可能性がある。中断し、ユーザーに伝えて、時間を置くか確認する。ロックがなければ、auto-dream の設定までは確かめなくてよい。
4. サブエージェント用メモリ（`.claude/agent-memory/`、`.claude/agent-memory-local/`、`~/.claude/agent-memory/`）は既定では対象外。棚卸しの報告で存在だけを伝え、ユーザーが指定したときに同じ手順で扱う。

## 2. 棚卸し（変更しない）

### 2.1 機械的な事実を集める

```bash
python3 <skill-dir>/scripts/inventory.py [--dir <memory-dir>] [--project-root <root>]
```

件数（`MEMORY.md` を除く個別メモリの数）、大きさ（索引と、索引を含む全体）、読み込み上限との距離、索引の壊れた行・索引にないファイル・`description` を繰り返している行・150 字を超える行、ファイルごとの壊れた `[[リンク]]`、見つからないパス、日付の数、文面の重なりが出る。
見つからないパスは「プロジェクトのルートと追跡ファイルのどこにもない」という意味で、別リポジトリのパスや、移動・削除されたファイルが含まれる。文面の重なりは手がかりにすぎず、意味の重複は本文を読んで判断する。

### 2.2 すべてのメモリを読む

`MEMORY.md` と個別メモリをすべて読む。各メモリを、中の主張の単位に分けて扱う。1 件のメモリに原則・事例・経緯・パスが混ざっていることが多い。

### 2.3 プロジェクト資料と照合する

主張ごとに、その内容がプロジェクト資料のどこに書かれているかを探す。探す先の例は次のとおり。

- `CLAUDE.md`（ルートとサブディレクトリ）、`.claude/rules/`、`AGENTS.md`、README、`docs/` 配下の規則・設計資料
- プロジェクト内のスキル（`.claude/skills/`）の本文
- SDD を使うプロジェクトなら、steering・rules・正典・テンプレート

資料ごとに、常に読み込まれるかどうかを確かめておく。起動時に読み込まれるのは、作業ディレクトリから上の階層にある `CLAUDE.md`、そこから `@path` で取り込まれるファイル、`paths` の指定がない `.claude/rules/*.md` である。サブディレクトリの `CLAUDE.md` や steering、設計資料、スキル本文などは、必要になったときに開く資料として扱う。

主張の中の固有の語（用語、ファイル名、閾値、禁止事項の動詞）で grep し、見つかった箇所は `file:line` か節名で記録する。
「同じことが書いてある」と判断するのは、資料の文がメモリの主張と同じ強度と範囲を持つときだけにする。資料の方が狭い・弱い場合は、差の部分がメモリに残る。

### 2.4 主張を分類する

| 分類 | 判定 | 処置 |
| --- | --- | --- |
| 委譲 | 資料に同じ強度と範囲で書かれている | 本文を消す。起動時に読み込まれる資料にあるものはリンクも残さない。必要なときに読む資料にあるものは、関連するメモリの中に 1 行のリンクだけ残す |
| 統合 | 別のメモリと同じ原則を言っている | 1 件にまとめる（§4.3） |
| 古い | 壊れたリンク、見つからないパス、完了した作業の予定、覆った決定、過去の事例の経緯と日付 | 消す。パスが移動しただけで主張が生きていれば、新しい場所を確かめて書き直す |
| 無関係 | 別のリポジトリや別の作業のメモ。プロジェクトの一部が別リポジトリへ移った後に残ったメモも含む | 相談する（§3）。移転先に同じ内容があるか確かめられれば、その場所を添える |
| 保持 | 資料に書かれていない作業上の判断基準（ユーザーの訂正から得た癖、進め方の好み、外部サービスの挙動） | 残す |

1 つの主張が複数の分類にまたがることは多い（一部は資料にあり、残りは別のメモリと重なる、など）。その場合は主張を分けて、それぞれに分類を付ける。

見つからないパスが本当に古いのか、別の場所に移っただけなのかは、`git log --all --oneline -- '<path>'` やファイル名の検索で確かめる。ファイルは移動先にあっても、その役割が別の資料に移っていれば、主張は古いものとして扱う。
外部のツールやサービスの挙動についての記録（「〜は動かない」「〜はブロックされる」）は、読み取りだけで確かめられる証拠（設定、その後の利用記録、公式の変更履歴）を探す。副作用のある操作で試さない。確かめられなければ、見つけた証拠を添えて「迷うもの」に回す。

## 3. 報告して了承を得る

次の形で報告する。表の各行は根拠を持つ。資料との重なりには `file:line`、古い記述には壊れたリンクや見つからないパスの実物を添える。

```markdown
## メモリの棚卸し（<プロジェクト>）

- 対象: `<memory-dir>`（<解決方法>）
- 件数 N 件／索引 L 行・X KB（上限 200 行・25KB）／全体 Y KB

### 統合の案
| 新しいメモリ | 元のメモリ | 残す判断基準の要約 |

### 手を入れずに（または削るだけで）残すもの
| メモリ | 削る部分 |

### プロジェクト資料へ委譲する主張
| メモリ | 主張 | 書かれている場所 |

### 削除する古い記述
| メモリ | 記述 | 古いと判断した根拠 |

### 相談したいもの
（下の相談の形で 1 件ずつ）

### 整理後の見込み
件数 N→M 件／索引 X→X' KB／全体 Y→Y' KB
```

迷うものは、理由と選択肢を添えて 1 件ずつ尋ねる。AskUserQuestion が使えるならそれを使い、1 回に 1 件（関連が強いものでも 4 件まで）にする。選択肢は「削除」「残す」「別の形で残す（例: 1 行に縮めて統合先へ入れる）」のように、実行内容が決まる形にする。

了承の範囲を確かめる。ユーザーが一部だけを了承したら、その部分だけを実行する。

## 4. 実行する

### 4.1 バックアップ

変更の前に、メモリディレクトリの外へ丸ごとコピーする。

```bash
dest="$HOME/.claude/memory-backups/$(basename "$(dirname "<memory-dir>")")/$(date +%Y%m%d-%H%M%S)"
mkdir -p "$dest" && cp -Rp "<memory-dir>/." "$dest/" && ls "$dest" | wc -l
```

コピーした件数が元と一致することを確かめる。このディレクトリは Claude Code が管理していないので、ユーザーが消すまで残る。保存先は最後の報告に書く。

### 4.2 frontmatter の扱い

- 新しく書くメモリの形式は、システムプロンプトの auto-memory の節の形式に従う（`name`・`description`・`type` など）。
- 既存のファイルにある `originSessionId`・`modified`・`node_type` などはハーネスが書き足す値で、手で作らない。統合先に既存のファイルを使うときは、そのファイルの frontmatter を保ったまま本文と `description` を書き換える。
- `type` は統合後の本文に合うものにする。統合元の `type` が食い違うなら、同じ原則かどうかを疑い直す。

### 4.3 統合したメモリを書く

- まとめる単位は、そのメモリを開く場面（validate を行うとき、文書を書くとき、並行エージェントを動かすとき、など）にする。事象ごとの細かい原則を 1 件ずつ残すと、索引が長くなり、同じ場面で読むべきメモリが散らばる。
- 1 件のメモリには、その場面で使う判断基準だけを入れる。
- 残すのは判断基準そのもの。具体的な事例、経緯、日付、spec やタスクの番号は書かない。判断基準を理解するのに事例が要る場合だけ、日付と固有名詞を落とした 1 文で書く。
- 自分のメモリ規約が `**Why:**`・`**How to apply:**` を求めていれば、統合元の理由を 1 つにまとめて書く。
- 委譲した主張の代わりに置くリンクは、書く前に `test -e <path>` か `grep -n '<節名>' <file>` で実在を確かめる。
- `[[name]]` のリンクは、統合後に残るメモリの `name` を指すように書き換える。

### 4.4 古いファイルを消す

統合元のファイルと、全体が委譲・削除になったファイルを消す。消す前に、そのファイルを `[[name]]` やパスで参照している残りのメモリがないかを grep する。

### 4.5 索引を書き直す

- 1 件 1 行、`- [タイトル](file.md) — 手がかり` の形にする。
- 手がかりは、そのメモリを開くべき場面を思い出させる短い語句にする。`description` の文を縮めて繰り返さない。目安は 1 行 150 字以内。
- 索引に本文を書かない。

### 4.6 検算する

もう一度 `scripts/inventory.py` を実行し、次を確かめる。

- 壊れた `[[リンク]]`、索引の壊れた行、索引にないファイルが 0 件
- 見つからないパスは、意図して残したもの（別リポジトリの参照など）だけ
- `description` を繰り返している索引の行がない

## 5. 最後の報告

```markdown
## メモリ整理の結果

- バックアップ: `<dest>`（ユーザーが消すまで残る）
- 件数 N→M 件／索引 L→L' 行・X→X' KB／全体 Y→Y' KB

### 統合
| 新しいメモリ | 元のメモリ |

### 委譲（本文を消し、リンクだけ残したもの）
| 主張 | リンク先 |

### 削除
| ファイルまたは記述 | 理由 |

### 相談の結果
| 対象 | 決定 |
```

戻したいときは、バックアップからファイルをコピーし直せばよいことも伝える。

## 組み込みの auto-dream との関係

Claude Code 2.1.270 のバイナリには、公開ドキュメントに載っていないバックグラウンド統合（設定名 `autoDreamEnabled`）が入っている。公開されている抽出プロンプト（2.1.235 時点）を見る限り、これは了承を取らずにメモリを統合・削除し、プロジェクト資料との照合は CLAUDE.md との矛盾の解消に限られる。
このスキルは、了承を取ること、資料全体への委譲とリンク先の実在確認、迷うものの相談を受け持つ。両者が同時に同じディレクトリを書き換えないよう、§1 で `.consolidate-lock` を確かめる。
